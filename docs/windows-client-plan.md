# Windows 多平台发布客户端：功能与技术方案

方案日期：2026-11-13。本文基于本地 fork 的代码和上游仓库公开文档梳理。下述功能清单是完整目标；本轮已落地的桌面底座及验证边界见 [desktop-development.md](desktop-development.md)，真实账号登录与发布仍未验收。

## 1. 已确认的目标

- 交付 Windows 桌面安装包。
- 覆盖项目现有全部国内外平台，共 17 个平台入口，Facebook 与 Facebook Page 分开处理。
- 提供视频、图文、文章三种创作和发布流程；每个平台展示其实际支持的内容类型。
- 先明确功能和技术方案，再开始业务代码开发。
- 以当前 fork 为开发基础，保留后续同步上游平台修复的空间。

尚未指定的产品细节暂按以下方案设计：本机运行、本地存储账号会话和素材信息；以本机多账号管理为主。云端服务和多人协作需要另外定义需求。

上游：[dreammis/social-auto-upload](https://github.com/dreammis/social-auto-upload)。本地仓库当前 origin 为 `Kat3r1naK/social-auto-upload-ui`，当前提交为 `3847fff`。此次没有拉取、合并或修改远程配置。

## 3. 功能清单

### 3.1 工作台

- 展示本地账号数量、待执行任务、正在执行任务、待处理异常和最近发布记录。
- 提供新建视频、图文、文章任务入口。
- 展示实际任务统计；平台播放量、收益、粉丝增长等数据需要独立的数据采集能力，不能由上传结果推导。

### 3.2 账号管理

- 一个平台注册多个账号，维护账号别名、分组和备注。
- 根据平台提供二维码登录或打开浏览器登录，显示登录进度和超时状态。
- 区分未验证、有效、失效、需要用户操作等状态，记录最近检查时间。
- 支持重新登录和解除本地绑定；解除绑定与删除平台账号是不同操作。
- 对短信验证、扫码确认等情况提供任务关联的处理入口；验证码不再依赖全局 `verify_code.txt`，避免账号间串用。
- 登录会话保存在当前 Windows 用户的数据目录，普通前端页面不接触原始 Cookie。
- 网络代理按平台配置，并为确有需要的账号保留覆盖配置；是否支持由具体适配器决定。
- Facebook Page 在账号之外明确选择目标 Page，执行前再次展示发布身份。

### 3.3 素材与内容

- 支持拖拽和选择本地视频、图片及文章文件，预览、分组和搜索。
- 默认记录本地文件引用，发布时直接读取文件，避免通过本地 HTTP 重复上传大视频。
- 创建任务及执行任务前校验源文件是否存在或发生变化，缺失时允许重新定位。
- 视频：标题、简介、标签、封面和平台专有参数。
- 图文：图片排序、封面、标题、正文和标签，显示对应平台的数量及长度限制。
- 文章：Markdown 编辑与预览、HTML/TXT 导入、正文插图、封面和已有主题；导入后保留图片资源的相对路径关系。
- 草稿自动保存，复用常用标题、正文和标签模板。
- 本地草稿是客户端保存的内容；平台草稿、仅填写不发表等选项仅在已有适配器支持时展示。

### 3.4 发布中心

基本流程：选择内容类型 → 导入或编辑内容 → 选择平台和账号 → 调整各平台内容 → 校验 → 查看发布清单 → 加入队列。

- 一份内容可以分发给多个兼容平台和账号，每个平台允许独立修改标题、正文、标签及封面。
- 视频、图文和文章分别校验，禁止将不兼容内容加入目标平台。
- 平台专有参数以高级选项展示，例如 B 站分区、YouTube 可见性和播放列表、Facebook Page 目标页面。
- 根据适配器支持展示原创声明、合集、商品信息、来源标注、背景音乐等选项。
- 提交清单明确展示账号、内容、目标平台、立即或定时方式，并为每个目标创建独立子任务。

### 3.5 任务中心

- 队列、子任务、执行次数和日志存入 SQLite；关闭页面不会丢失记录。
- 同一账号的登录及发布任务串行执行；不同账号可在全局并发上限内执行。
- 显示准备、登录检查、上传、填写、提交和核验等实际阶段；只有取得真实上传进度时才显示百分比。
- 支持取消排队任务、停止继续分发、对运行任务请求安全取消。平台已经接受的发布需要单独执行平台作品操作。
- 仅对明确未提交的失败允许直接重试；提交后发生断线、超时或进程退出时先进入待核验状态，避免盲目重复发布。
- 重启后恢复队列和历史；中断任务根据执行阶段标记为可重试或待核验。恢复任务不等于恢复平台上传字节进度。
- 用户验证按任务暂停等待，不阻塞其他可执行账号的任务。

建议区分两个维度：

- 任务状态：排队、运行、等待用户、成功、失败、取消、中断、待核验。
- 作品状态：未知、已提交、已设置平台定时、审核中、已公开、审核失败。平台无法查询的状态保持未知。

### 3.6 定时发布

- 平台原生定时：现在上传并提交给平台，由平台在指定时间发表；平台接受后不要求客户端持续运行。
- 本地定时执行：指定时间由客户端启动上传；要求电脑开机、未休眠、客户端后台运行且网络可用。
- 最小提前时间、最大时间范围、时间间隔和时区按平台校验。界面展示所采用的时区，内部保存可转换的明确时间。
- 重启后发现错过执行时间的本地任务，先标记为已错过，提供重新安排入口。
- 知乎实验性原生定时明确标注；YouTube 原生定时仍按未完成能力处理，本地定时不能冒充平台原生能力。

### 3.7 发布记录与平台作品

- 记录每个子任务的账号、内容、时间、结果、作品编号及链接（平台能够返回时）。
- 区分平台接受提交和审核后公开，展示对应证据及最近核验时间。
- 提供失败原因、步骤日志、截图和诊断信息导出。
- 对已有能力提供作品核验、删除、移至回收站或取消原生定时等入口，逐平台展示。
- 删除平台作品前展示具体目标并确认；任务取消不能替代平台删除。

### 3.8 设置与桌面体验

- 素材目录、用户数据目录、代理、浏览器运行方式及并发上限。
- 托盘运行、关闭窗口后的行为、退出时正在执行任务的处理。
- 启动时检查服务和运行时，提供明确错误及修复入口。
- 显示客户端版本、上传核心版本和浏览器运行时版本，升级时保持兼容并迁移数据库。
- 客户端统一准备 Python、自动化浏览器、文章渲染依赖和 Bilibili 工具，普通使用者无需手工配置开发环境。

## 4. 实施技术选型

用户要求使用 TypeScript 后，新增桌面业务也统一使用 TS：任务服务与 SQLite 由 Electron 主进程管理，通过受限 IPC 与 Vue 通信。Python 仅承担原有上传核心的独立 worker。首版本机单窗口因此不再增加 FastAPI/HTTP 服务；以后需要独立 API 或远程管理时再扩展。

| 层级 | 选择 | 原因 |
| --- | --- | --- |
| Windows 桌面壳 | Electron | 复用现有 Web 界面，承接窗口、托盘、文件选择和本地服务生命周期 |
| 界面 | Vue 3 + TypeScript + Vite + Element Plus | 延续现有框架；新增代码通过类型约束表达平台能力和任务状态 |
| 界面状态与路由 | Pinia + Vue Router | 与现有工程一致 |
| 本地业务 | TypeScript + Zod，运行在 Electron 主进程 | 管理账号、素材、草稿、队列及运行时参数校验 |
| 平台执行 | 独立 Python worker 进程 + 平台适配器 | 隔离浏览器任务，便于进程清理和中断恢复 |
| 自动化 | 沿用各平台现有 Patchright / Playwright，B 站沿用 biliup | 保持现有能力，分别验证驱动兼容性 |
| 持久化 | SQLite，通过 Node 内置 node:sqlite 访问 | 不引入额外原生数据库扩展；使用事务、WAL 和 user_version 管理数据库 |
| 通信 | 类型化 Electron IPC + worker 请求/结果文件 | 前端不接触原始 Cookie，不暴露通用 IPC、终端或文件系统接口 |
| Python 打包 | PyInstaller，优先 onedir | 携带解释器和依赖，便于检查驱动、数据文件和子进程资源 |
| Windows 安装包 | electron-builder + NSIS | 生成安装程序、快捷方式和卸载入口 |

Electron 的取舍是安装包和运行内存开销较大。选择它是基于现有 Vue 工程及桌面进程管理需求；实际包体和内存占用需要原型打包测量。Tauri 同样支持 Python sidecar，但会引入 Rust 工具链；pywebview 也能复用 Vue 和 Python，若后续更强调轻量安装，可作为替代方案评估。

所有正式任务记录由 TS 服务统一写入 SQLite；Vue 通过 IPC 提交命令，Python worker 返回结构化执行结果，不直接写数据库。当前桌面业务不监听网络端口。浏览器预览仍可兼容旧 Flask 服务，两个入口分别处理。

任务先持久化，再由主进程调度独立 worker；同账号串行，最多并发两个发布任务，账号登录/检查与同账号发布互斥。中断和结果不明的任务进入待核验，不自动重试。定时使用明确时刻保存，错过的任务不会自动补发。

桌面包包含 Python worker、Patchright / Playwright 各自匹配的 Chromium、biliup 和文章渲染依赖。文章渲染显式调用 Electron 内置的 Node 运行方式，不依赖用户 PATH 中存在 node、npm 或 Python。原项目 CLI 继续保留原来的外部 Node 行为。

## 5. 与原项目的关系

建议增加以下边界，尽量降低后续同步上游的冲突：

```text
desktop/                     Electron、TS 服务、SQLite、preload、构建与测试
desktop/python/              Python worker 与上游回归检查
shared/                      前端和桌面端共用的平台能力、IPC 类型
sau_frontend/                Vue + TS 界面，浏览器兼容旧服务
uploader/                    尽量保留上游平台实现
sau_commands/                复用已有可调用函数，保留 CLI 兼容
```

- 适配器把账号、发布请求、执行事件和结果转换成统一协议，不解析终端日志来猜测成功。
- 一部分平台已有可直接调用的业务函数；其余平台需要包装 uploader。TikTok 作为单独适配项处理。
- 对路径、验证码、二维码回调和结构化结果所需的核心修改集中处理，并保持 CLI 行为兼容。
- 平台能力由后端适配器提供，前端据此展示字段，避免将 17 套能力重复写在页面里。
- 使用独立功能分支开发客户端；上游同步通过适配器回归验证，客户端更新不能直接替换成未经验证的最新上传核心。

## 6. 开发顺序与验收

以下是同一交付范围内的开发顺序，不是将部分平台或内容类型移出首版范围：

1. 固化功能清单、平台能力结构、任务状态与页面流程。
2. 提前完成打包原型：验证 Vue 窗口、TS 服务、Python worker、浏览器运行时、Markdown 渲染及退出后的进程清理，尽早确认分发方案可行。
3. 完成账号、素材、草稿、发布表单、队列、日志及历史的通用能力。
4. 按平台逐个接入其支持的内容组合，全部 17 个平台都保留验收项；专有参数与管理操作随适配器接入。
5. 完成定时、验证码交互、中断恢复、待核验处理和兼容迁移。
6. 在没有 Python、Node.js 开发环境的 Windows 测试机验证安装、升级、运行和卸载，再形成正式安装包。

关键验收：

- 每个平台能完成其实际支持的登录、账号检查和内容发布流程。
- 一个批次中部分目标失败，其他目标仍能独立完成；结果逐账号记录。
- 同一账号不会被两个上传任务同时操作。
- 任务等待用户验证时，其他账号仍可按并发规则执行。
- 程序重启后任务和草稿可恢复；提交结果未知的任务先核验，不自动重发。
- 平台原生定时与本地定时的执行条件清晰，错过的本地任务有明确状态。
- 安装或升级不会覆盖用户账号会话、草稿、素材引用及发布记录。
- 每个目标的真实登录和发布验收需要可用账号及对应内容；缺少账号时应记录为未验证，不能以页面可点击代替端到端验收。

正式开发前仍可调整的产品细节包括名称与视觉风格、是否需要富文本文章编辑、素材是否默认复制进库、安装包是否要求离线安装。本文先采用可继续推进通用架构的默认方案。
